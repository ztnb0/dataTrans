# 轮巡方式下的即时同步操作（sync-lunXun）

> 本文档描述「数据变化即时同步」的**轮巡（轮询）方案**：后台定时轮巡，检查三个数据源的表单是否有新增/修改，再即时同步到简道云。
> 取代此前的「接口回调」方案（对方业务系统主动调本工具接口，见 `docs/功能：创建即时同步接口.md` / `docs/接口对接说明.md`）。
> 核心同步流程沿用 `docs/sync-feature-plan.md` 的「五、技术方案 → 2. 同步流程」，本文档在其基础上**新增轮巡时间限制**，并把方案落地细节、涉及的数据源、改动点说清楚。

---

## 一、背景与目标

### 为什么从「接口回调」改回「轮巡」

之前定的方案是：对方业务系统在 INSERT / UPDATE 成功后，主动回调本工具的 `POST /api/sync/notify-batch` 接口，把变化行直接传过来。

与老师沟通后确认该方案有问题：

| 问题 | 说明 |
|---|---|
| 三个平台都要改造 | 大平台、教务、飞霞 3 个平台**各自**都要在业务代码里加接口调用，工作量大 |
| 平台多了更麻烦 | 以后每新增一个数据源平台，都要对方再做一次接口对接，不可持续 |
| 依赖对方配合 | 对方不调用或调用失败，数据就漏同步，本工具无法兜底 |

因此**决定暂停接口回调方案，改回后台轮巡**：本工具自己定时去查三个数据源的表，发现变化就同步到简道云，不依赖对方做任何改造。

### 目标

1. 后台定时轮巡，检查三个数据源的表是否有**新增 / 修改**；
2. 发现变化后**即时增量同步**到简道云对应表单；
3. 增加**轮巡时间限制**：晚上 20:00 ~ 次日 08:00 不轮巡，其余时间段每 5 分钟轮巡一次。

---

## 二、总体方案（一张图）

```
后台常驻轮巡线程（随服务启动）
   │
   ├─ 每一轮循环：
   │     1. 判断当前时间是否在「轮巡时间段」内？
   │        ├─ 否（20:00 ~ 次日 08:00）→ 睡到下次 08:00 再醒，跳过本轮
   │        └─ 是（08:00 ~ 20:00）   → 进入第 2 步
   │     2. 根据「自动同步开关」决定本轮跑哪些映射：
   │        ├─ 开关 = 全部  → 跑所有 enabled 映射
   │        ├─ 开关 = 单源  → 只跑被开启的那几个数据源下的映射
   │        └─ 都没开       → 本轮跳过，不查库不同步
   │     3. 逐个同步（run_one_mapping），写日志
   │     4. 睡 5 分钟，回到第 1 步
```

关键点：
- **不依赖对方平台任何改造**，全部由本工具完成；
- **三套数据源共用同一套轮巡逻辑**，检测方式统一为「主键递增 + hash 对比」（见第七节）；
- **自动同步由前端按钮控制**（见第八节）：默认**不自动同步**，前端「单源同步」「全部同步」两个按钮开启/暂停，对应后端内存开关 `AUTO_SYNC`（重启后回到关闭）；
- **旧接口暂停**：`POST /api/sync/notify`、`POST /api/sync/notify-batch` 不再作为主要同步手段（见第十二节）。

## 三、轮巡时间限制（本次唯一新增需求）

### 1. 规则

| 时间段 | 是否轮巡 | 说明 |
|---|---|---|
| 08:00 ~ 20:00 | ✅ 轮巡 | 每 5 分钟一轮 |
| 20:00 ~ 次日 08:00 | ❌ 不轮巡 | 后台休眠，不查库、不同步 |

- **判断依据**：服务器本地时间（北京时间）。
- **边界处理**：
  - `08:00` 起进入轮巡时间段（含 08:00 整）；
  - `20:00` 起进入休眠时间段（含 20:00 整，即 `hour >= 20 or hour < 8` 判定为不轮巡）。

### 2. 时间窗口判断（伪逻辑）

```text
now = 当前本地时间
if now.hour >= 20 或 now.hour < 8:
    不轮巡，休眠到「下一个 08:00」
else:
    执行一轮同步，然后休眠 5 分钟
```

### 3. 休眠策略

| 场景 | 动作 |
|---|---|
| 轮巡时间段内 | 每轮完成后睡 `5 分钟`，再判断时间 |
| 休眠时间段内 | 直接睡到「下一个 08:00」（不空转 5 分钟），到点自然进入轮巡 |

### 4. 配置化（建议）

把轮巡参数抽成配置，方便以后调整，例如在 `config.json` 增加：

```json
{
  "sync": {
    "enabled": true,
    "interval_minutes": 5,
    "off_start": "20:00",
    "off_end": "08:00"
  }
}
```

| 配置项 | 默认 | 含义 |
|---|---|---|
| `enabled` | true | 是否开启轮巡 |
| `interval_minutes` | 5 | 轮巡间隔（分钟） |
| `off_start` | 20:00 | 休眠开始时刻（含） |
| `off_end` | 08:00 | 休眠结束时刻（不含，即次日 08:00 恢复） |

> 若暂不做配置化，也可先写成常量，但建议留成配置，方便老师日后改时间。

## 四、同步流程（每次轮巡，对每套映射）

> 沿用 `docs/sync-feature-plan.md`「五、技术方案 → 2. 同步流程」。此处按「映射」为单位逐套执行。

对 `mappings.json` 中每一套 `enabled=true` 的映射，依次执行：

### 1. 对账（首次，仅当该映射在 `sync_state.json` 中无记录 / `max_id` 为空时）

- 拉取简道云该「数据类型」下的已有数据，建立 `源表主键 ↔ data_id` 对应关系；
- 源表全量读入，按「源表主键」匹配：
  - 已在简道云的 → 记下 `data_id` + 字段值 hash（接管）；
  - 不在的 → 标记为待新增；
- 结果写入 `sync_state.json`（记录 `max_id`、`rows`、`last_sync_time`）。

> ⚠️ 匹配键说明：本方案用「**源表主键 + 数据类型**」作为简道云里定位数据的唯一键（与现有 `jdy_find_by_id` 逻辑一致）。
> 早期 `sync-feature-plan.md` 曾写「对账唯一键 = 项目编号」，但飞霞表的「项目编号」（批次号）在多行间会重复，不能作为唯一键，故统一改用**源表主键**（`id` 字段存的就是源表主键）。

### 2. 增量检测

| 变化类型 | 检测方式 | 同步动作 |
|---|---|---|
| 新增 | 主键递增：`主键 > max_id` 的行 | `batch_create` 批量新增，记录返回的 `data_id` |
| 修改 | 轻量全量拉「主键 + 映射字段」算 hash，与快照对比 | 单条 `update` |

- 新增走 `batch_create`（返回 `success_ids` 顺序对应）；
- 修改走单条 `update`（简道云 `batch_update` 只能改固定值，不能逐条设不同值，故逐条 update）；
- **查重覆盖**：写入简道云前先按「主键 + 数据类型」查是否已存在——已存在则 `update` 覆盖，不存在才 `batch_create`，避免重复（对账用已拉取的 `jdy_map` 查重，增量新增逐条 `jdy_find_by_id` 查重）；
- 转换规则（飞霞 `batch_number` / `city_name`）在组装简道云记录时套用；`city_name` 命中「在线考试 / 其他」返回 `None` 的行**跳过不传**（沿用现有 `apply_transform` / `build_jdy_record` 逻辑）。

### 2.1 hash 对比机制（每条数据怎么比）

关键结论：**只有源表做 hash，简道云不做 hash。**

每轮对**源表每一条数据**算一次 hash，和 `sync_state.json` 里存的**上一次快照 hash** 逐条对比——不是拿源表和简道云逐条比。

以 `coaching_class`（映射字段 `id / class_name / class_ctime / class_number`）为例，`sync_state.json` 里每行存两个值：

```json
"rows": { "3387": { "data_id": "6aa39876a338309858a042c2", "hash": "abc123" } }
```

- `data_id`：简道云内部编号，**仅用于 update 时定位**；
- `hash`：上一次同步时，源表这行 4 个字段值算出的 md5。

每轮轮巡的对比流程：

```
1. 全量读源表：SELECT id, class_name, class_ctime, class_number FROM coaching_class
2. 对每行，用这 4 个字段值算一个新 md5（如 "def456"）
3. 拿主键 3387 去 rows 里取旧 hash "abc123"
4. 比较：
     新 "def456" == 旧 "abc123" → 没变，跳过
     不等 → 源表这行被改过 → 用 data_id "6aa3..." 调 update 更新简道云
              → 再把 rows["3387"]["hash"] 改成 "def456"（记新快照）
```

为什么不对简道云做 hash：
1. 简道云查一条数据就要一次 API 调用，9481 行要几百次分页请求，慢且没必要；
2. 要检测的是「源表变没变」，不是「源表和简道云差多少」——每次 update 后简道云的值 == 当时源表的值，所以「源表现在 vs 源表上次快照」已经等价于「有没有变化」；
3. 简道云全程只当「接收方 + data_id 提供方」，不参与比对。

> 说明：早先想给 `groupbatch` 用 `mtime`（时间戳 > 上次时间）来筛改过的行，能少算 hash；但实测 `mtime` 列对 `dptep` 无 SELECT 权限，故全部退化为「全量每行算 hash 对比」，逻辑一致，只是每轮多算几次 md5（依然 < 1 秒）。

### 3. 更新同步状态

同步完成后刷新该映射在 `sync_state.json` 里的：

- `max_id`（更新为本次同步到的最大主键）；
- `rows`（`主键 → { data_id, hash }`）；
- `last_sync_time`（本次同步完成时间）。

## 五、数据文件设计

### 1. `mappings.json`（已存在，界面「保存映射」写入）

当前已配置 6 套映射（见第八节），字段：`id / source / database / table / source_fields / target_fields / transforms / platform_value / data_type_value / enabled`。

轮巡只处理 `enabled=true` 的映射；关闭映射（`enabled=false`）即暂停该表的同步。

### 2. `sync_state.json`（新增，后台自动维护）

按映射 id 记录同步状态：

```json
{
  "<mapping_id>": {
    "max_id": 12715,
    "last_sync_time": "2026-09-16 10:30:00",
    "rows": {
      "3387": { "data_id": "xxx", "hash": "abc123" }
    }
  }
}
```

| 字段 | 含义 |
|---|---|
| `max_id` | 上次同步到的最大主键（新增检测用） |
| `last_sync_time` | 上次同步完成时间（状态记录用，不再用于修改检测） |
| `rows` | `主键 → { data_id, hash }`（定位简道云数据 + 修改检测用） |

> 这个文件就是轮巡的「账本」，记三类账：
> - **记到哪儿了**：`max_id`，下次只查 `主键 > max_id` 即为新增，避免全表扫；
> - **记对应关系**：`rows[主键].data_id`，存「源表主键 ↔ 简道云 data_id」，更新时才知道改简道云里哪条；
> - **记旧值**：`rows[主键].hash`，存源表该行字段值的哈希，下次对比判断是否被修改。

### 2.1 三个易混概念的澄清

| 概念 | 澄清 |
|---|---|
| `data_id` | 是**简道云自己给每条数据分配的内部唯一编号**（简道云生成，写入/查询时才返回）。**不是**「源表主键 + 项目编号」，跟源表主键、项目编号都无关。 |
| 匹配键（定位用） | 定位简道云里某条数据，用的是「**源表主键（存简道云 `id` 字段）+ 数据类型**」组合 filter（现有 `jdy_find_by_id` 逻辑）；查到后才拿到它的 `data_id`。「项目编号」只是业务字段，不参与定位。 |
| `hash` | 算的是**源表某一行**（主键 + 映射源字段）的哈希，**不是**简道云某行的哈希；只用于判断源表这行有没有被改。 |

## 七、各表检测策略（统一）

6 套映射统一采用「主键递增（新增）+ 轻量全量 hash 对比（修改）」：

| 表 | 新增检测 | 修改检测 | 备注 |
|---|---|---|---|
| `groupbatch`（大平台期次） | 主键递增 `id > max_id` | 轻量全量 hash 对比 | `mtime` 列对 `dptep` 无 SELECT 权限，改用 hash |
| `coaching_class`（大平台班级） | 主键递增 `id > max_id` | 轻量全量 hash 对比 | 无时间戳字段 |
| Oracle `CLAZZ`（BFEC/SHFEC/GZFEC） | 主键递增 `CLASS_ID > max_id` | 轻量全量 hash 对比 | 无时间戳、账号仅 `CREATE SESSION` |
| `db_plan_positon`（飞霞） | 主键递增 `PlanPositonID > max_id` | 轻量全量 hash 对比 | 带转换规则；`PlanPositonID` 有主键索引，增量查询快 |

> 轻量全量 hash 对比只查「主键 + 映射的 3~4 个字段」（非 `SELECT *`），数据量最大的 CLAZZ 三 schema 合计约 9481 行、< 1 秒，5 分钟一次无压力。

## 八、后端改动点（已实现）

1. **后台轮巡线程**：随 FastAPI 启动（startup 事件）拉起一个 daemon 线程，循环「时间判断 → 按开关选映射 → 逐映射同步 → 写日志 → 休眠」。
2. **时间窗口判断函数**：`now.hour >= 20 or now.hour < 8` → 休眠到次日 08:00；否则进入轮巡。
3. **自动同步开关（内存态）**：`AUTO_SYNC = {'all': bool, 'sources': {数据源id: bool}}`，由前端按钮控制；`_mappings_to_run()` 据此决定本轮跑哪些映射（全部 / 指定数据源 / 跳过）。**默认全关，重启后回到关闭**。
4. **`sync_state.json` 读写**：`load_sync_state()` / `save_sync_state()`，按映射 id 存 `max_id / last_sync_time / rows`。
5. **对账逻辑**：首次（无状态）按源表主键匹配简道云已有数据，建立 `data_id` + hash 快照。
6. **增量检测**：主键递增 + 轻量 hash 对比（见第七节），并带 `时间字段 >= 2026` 的时间筛选（只同步 2026 年及之后的数据）。
7. **同步执行（查重覆盖）**：写入简道云前先按「主键 + 数据类型」查重——已存在则 `update` 覆盖，不存在才 `batch_create`，避免重复数据（对账用 `jdy_map` 查重，增量新增用 `jdy_find_by_id` 查重）。
8. **接口**：
   - `GET /api/sync/auto/status`：查询自动同步开关状态；
   - `POST /api/sync/auto/toggle`：切换开关（`mode=single` + `source`，或 `mode=all`）；
   - `POST /api/sync/run`：手动触发（保留，供调试）；
   - `GET /api/sync/status`：查看各映射同步状态；
   - `POST /api/sync/reset`：重置指定映射的同步状态（删 `sync_state.json` 里该映射记录，下次重新对账）。
9. **前端**：左栏「预览源数据」旁加「**单源同步**」「**全部同步**」「**重置同步**」三个按钮；「同步」开启时**先立即同步一次**再进入每 5 分钟自动轮巡（文字在「同步/暂停」间切换）；「重置同步」清空当前选中表单的同步状态。
10. **日志**：同步结果写 `sync.log`（见第九节）。

---

## 九、日志

- 暂不做「同步任务面板」，用**日志文件**查看轮巡结果；
- 每轮 / 每套映射记录：时间、映射 id、新增 N 条、修改 N 条、跳过 N 条、失败 N 条、错误信息；
- 便于事后确认「某次轮巡到底同步了什么、有没有报错」。

---

## 十、风险点与注意

1. **对账只做一次**：首次对账建立 `data_id` 映射后持久化，之后不再对账。若期间有人手动改简道云数据，映射会失真。
2. **源表删除不同步**：简道云 `delete` 未授权，源表删除的行不会在简道云删除。
3. **主键重复**：各表主键表内唯一，已满足；若源表新数据出现主键重复会告警并跳过。
4. **单条 update 性能**：同一轮大量行被修改时逐条 update 会慢，但增量场景变化量小，可接受。
5. **跨零点休眠**：20:00 ~ 次日 08:00 跨越午夜，时间判断用 `hour >= 20 or hour < 8`，不要写成 `20 <= hour <= 8`。
6. **时区**：以服务器本地时间（北京时间）为准，服务器时间不准会导致轮巡窗口偏移。

## 十二、术语速查

| 术语 | 含义 |
|---|---|
| 轮巡 | 后台定时自动查源库变化并同步（本方案，5 分钟一轮 + 夜间休眠） |
| 轮巡时间段 | 08:00 ~ 20:00，执行轮巡 |
| 休眠时间段 | 20:00 ~ 次日 08:00，不轮巡 |
| 对账 | 首次运行，把简道云已有数据与源表按主键对应，补记 data_id |
| 增量同步 | 只同步新增/修改，不全量重传 |
| data_id | 简道云每条数据的内部唯一编号（简道云生成，不是源表主键 + 项目编号） |
| 主键递增 | 用 `主键 > 上次最大值` 判断新增 |
| hash 对比 | 对**源表某行**的字段值算哈希，与上次快照比对判断是否修改（与简道云无关） |
| 匹配键 | 定位简道云数据的唯一组合（本方案用「源表主键 + 数据类型」，存简道云 `id` 字段） |
| 账本 | `sync_state.json`，记录 `max_id`（记到哪儿）+ `rows`（对应关系 + 旧值）+ `last_sync_time` |
