# 功能：创建即时同步接口

> 分支：`feature/表单数据的即时同步功能`
> 本文档描述「即时同步接口」功能：对方业务系统在写库后主动回调本工具接口，本工具回查数据库后把变化写入简道云。
> 与本文档相关的历史讨论见 `docs/sync-feature-plan.md`（含五之补充、五.一 的 CDC 突破方案）。

---

## 一、背景与目标

### 背景

此前在 `sync-feature-plan.md` 中规划过三种实现"数据变化即时同步"的技术路线，经与老师沟通，逐条收敛如下：

| 路线 | 结论 |
|---|---|
| 轮询（定时查库） | 实时性差、有数据库压力，且无回调的情况下才需要 |
| CDC（binlog / DTS / canal） | 太麻烦：需要权限、组件、Kafka 等，被否决 |
| **回调（对方改库后调接口）** | **最终选定**：最简单、最贴合业务 |

### 目标

对方业务系统在数据库上做**新增（INSERT）**或**修改（UPDATE）**并提交后，主动调用本工具的接口，本工具回查数据库最新值，把对应变化同步到简道云对应的表单字段。

---

## 二、方案概述

```
对方业务系统 INSERT/UPDATE 成功、commit 之后
  → 调本工具接口 POST /api/sync/notify（只传：哪张表 + 哪个主键）
  → 本工具回查数据库，拿到这一行最新值
  → 按映射写简道云（新增 batch_create / 修改单条 update）
```

核心设计原则：

1. **对方传得越少越好**：对方只传「表名 + 主键」，字段值由本工具回查数据库为准，避免对方拼字段出错、也保证永远与库一致。
2. **幂等**：对方可能重试、乱序，本工具靠「回查 + hash 对比」保证重复调用无副作用、最终一致。
3. **鉴权**：接口只在内网暴露，仍需 token 鉴权，防误调用。

---

## 三、接口契约

### 1. 地址与鉴权

| 项 | 值 |
|---|---|
| 方法 / 路径 | `POST /api/sync/notify` |
| 鉴权 | 请求头 `X-Sync-Token: <约定token>` |
| 协议 | HTTP，内网直连 |

### 2. 请求体

```json
{
  "table": "coaching_class",
  "pk": "123"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `table` | string | 源表名（如 `coaching_class`、`groupbatch`） |
| `pk` | string | 该行主键值（统一按字符串传，本工具侧按类型转换） |

### 3. 响应

| 场景 | 状态码 | 响应体 |
|---|---|---|
| 成功 | 200 | `{"ok": true}` |
| 鉴权失败 | 401 | `{"ok": false, "error": "invalid token"}` |
| 参数缺失 | 400 | `{"ok": false, "error": "..."}` |
| 处理异常 | 500 | `{"ok": false, "error": "..."}` |

### 4. 对方要做的事

在对方写库的代码里，insert/update 提交成功后加一行**异步**调用（不阻塞主业务，失败重试 2~3 次）：

```python
# 伪代码示意（对方语言自定）
def save_record(...):
    db.insert_or_update(...)   # 原有逻辑
    db.commit()
    # 新增：异步通知本工具，失败重试
    requests.post('http://<内网IP>:8088/api/sync/notify',
                  json={'table': 'coaching_class', 'pk': 123},
                  headers={'X-Sync-Token': '<约定token>'},
                  timeout=5)
```

## 四、后端实现逻辑

### 1. 处理流程（`POST /api/sync/notify`）

```
1. 校验 X-Sync-Token
2. 校验 table / pk 参数
3. 回查数据库该行（复用 get_conn + 现有查询逻辑）
4. 查 sync_state.json，主键是否存在 data_id
   ├─ 不存在 → batch_create 新增，记录返回的 data_id
   └─ 存在   → 比对 hash，值变了才单条 update
5. 更新 sync_state.json（data_id 映射 + hash）
6. 返回 {ok: true}
```

### 2. 新增 vs 修改的判断

| 主键在 sync_state.json 中 | 动作 |
|---|---|
| 无 `data_id` | `batch_create` 新增 → 记录返回的 `data_id` |
| 有 `data_id` 且 hash 不同 | 单条 `update` |
| 有 `data_id` 且 hash 相同 | 跳过（幂等，无变化） |

### 3. 需要新增/复用的代码（相对现有 `app.py`）

| 模块 | 说明 | 现状 |
|---|---|---|
| `POST /api/sync/notify` | 鉴权 + 回查 + 分流 + 幂等 | ❌ 新增 |
| 单条 `update` 函数 | 复用 `normalize_value` + 简道云地址/token | ❌ 新增 |
| `batch_create` | 已有 | ✅ 复用 |
| `get_conn` / 查询逻辑 | 回查该行 | ✅ 复用 |
| token 鉴权 | 约定 token，存 `.env` | ❌ 新增 |

## 五、状态文件设计

### 1. `mappings.json`（映射关系，界面/配置维护）

```json
[
  {
    "id": "coaching-class",
    "source": "dpt-aliyun",
    "database": "dptep",
    "table": "coaching_class",
    "platform_value": "教务系统",
    "source_fields": ["class_number", "class_name", "class_ctime"],
    "target_fields": ["_widget_1788918827860", "_widget_1788918827861", "_widget_1788918827862"],
    "time_field": "class_ctime",
    "enabled": true
  }
]
```

### 2. `sync_state.json`（同步状态，后台自动维护）

```json
{
  "coaching-class": {
    "rows": {
      "123": { "data_id": "668899", "hash": "xxxx" }
    },
    "last_sync_time": "2026-09-11 10:00:00"
  }
}
```

- `rows`：`主键 → { data_id, hash }` 对应关系；
- `hash`：对映射字段值算哈希，用于判断是否变化（幂等 + 修改检测）。

## 六、首次对账

CDC / 回调都只处理"之后发生的变化"，简道云里已有的存量数据需要先建立 `主键 ↔ data_id` 对应：

1. 用户用现有界面手动全量传输存量数据 → 简道云；
2. 跑一次对账：读简道云已有数据，按**项目编号**匹配，建 `主键 → data_id` 映射写入 `sync_state.json`；
3. 对账完成后，再让对方开启回调。

> 注意：对账期间若对方同时改数据会漏，需「先对账完成，再开回调」串行执行。

## 九、风险点

1. **回调漏掉**：无轮询兜底，若对方重试仍失败，该条数据会漏同步。建议二期补一个「对账/补传」手段。
2. **首启窗口遗漏**：对账与开启回调之间必须串行，否则窗口内变更会漏。
3. **主键/项目编号唯一性**：对账依赖项目编号唯一，若某表重复需另选键（见 `传输映射规则.md` 提示）。
4. **单条 update 限流**：简道云 `update` 20 次/秒，瞬时大量修改会排队，回调场景变化量小、可接受。
5. **删除不同步**：简道云删除接口未授权，源表删除无法同步。

## 十、术语速查

| 术语 | 含义 |
|---|---|
| 回调 | 对方写库后主动调本工具接口 |
| 回查 | 本工具收到通知后重新查数据库拿最新值 |
| 对账 | 首次把简道云已有数据与源表按唯一键对应，补记 data_id |
| data_id | 简道云每条数据的内部唯一编号 |
| hash 对比 | 对字段值算哈希，与上次快照比对判断是否修改 |
| 幂等 | 重复/乱序调用不产生副作用 |
