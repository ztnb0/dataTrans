# 功能：创建即时同步接口

> 分支：`feature/表单数据的即时同步功能`
> 本文档描述「即时同步接口」功能：对方业务系统在写库后主动回调本工具接口，把变化的行数据直接传过来，本工具按映射写入简道云。

---

## 一、背景与目标

### 背景

此前在 `sync-feature-plan.md` 中规划过三种实现"数据变化即时同步"的技术路线，经与老师沟通，逐条收敛如下：

| 路线 | 结论 |
|---|---|
| 轮询（定时查库） | 实时性差、有数据库压力，且无回调的情况下才需要 |
| CDC（binlog / DTS / canal） | 太麻烦：需要权限、组件、Kafka 等，被否决 |
| **回调（对方改库后调接口）** | **最终选定**：最简单、最贴合业务 |

### 目标

对方业务系统在数据库上做**新增（INSERT）**或**修改（UPDATE）**并提交后，主动调用本工具的接口，把变化的行数据（源字段名 + 值 + 主键）直接传过来，本工具按映射写入简道云对应表单字段。

### 适用范围

**三个数据源平台通用同一个接口**（接口是"表驱动"的，不绑定任何数据源）：

| 平台 | 数据源 | 表 | 备注 |
|---|---|---|---|
| 大平台后台系统 | MySQL（dpt-aliyun） | `coaching_class` / `groupbatch` | — |
| 教务系统 | Oracle（oracle-clazz） | `CLAZZ`（BFEC/SHFEC/GZFEC） | 需传 `database` |
| 飞霞系统 | MySQL（用户添加） | `db_plan_positon` | 带转换规则 |

---

## 二、方案概述

```
对方业务系统 INSERT/UPDATE 成功、commit 之后
  → 调本工具接口 POST /api/sync/notify-batch
    （传：表名 + job(增/改) + 行数据数组，行数据里含 pk + 源字段值）
  → 本工具按映射（含转换规则）组装简道云记录
  → job=2：batch_create 新增；job=1：按「id+数据类型」查 data_id 后 update
```

核心设计原则：

1. **对方直接传数据，本工具不回查数据库**：字段值由对方随请求附上，本工具不再去源库查这一行。
2. **job 区分增改**：`job=2` 增加、`job=1` 修改，由对方明确告知，本工具不再自己判断"在不在"。
3. **用「源表主键 + 数据类型」组合键定位**：简道云「id」字段存源表主键，与「数据类型」组合作为唯一匹配键（多张表主键会跨表重叠，单用主键会撞车）。
4. **无鉴权**：公司内网自用、接口不对外，不做 token 鉴权。

## 三、接口契约

### A. 主接口：`POST /api/sync/notify-batch`（对方直接传数据）

| 项 | 值 |
|---|---|
| 方法 / 路径 | `POST /api/sync/notify-batch` |
| 协议 | HTTP，内网直连，**无鉴权** |

请求体：

```json
{
  "table": "coaching_class",
  "database": "",
  "job": 1,
  "rows": [
    { "pk": "123", "class_number": "C001", "class_name": "二班", "class_ctime": "2026-09-11" }
  ]
}
```

| 字段 | 类型 | 说明 |
|---|---|
| `table` | string | 源表名 |
| `job` | int | `1`=修改（只传改动字段），`2`=增加（传全部字段） |
| `rows` | array | 一行或多行；每行含 `pk`（主键值）+ 源表真实列名与值 |
| `database` | string（可选） | MySQL 省略；**Oracle 必填**（CLAZZ 在 BFEC/SHFEC/GZFEC 三 schema 同名） |

> **job=1（修改）**：只需 `pk` + 改动字段，没传的字段简道云保持不变。
> **job=2（增加）**：需 `pk` + 全部业务字段。

响应：

```json
{ "ok": true, "job": 1, "success": 1, "fail": 0, "skipped": 0,
  "results": [ { "pk": "123", "ok": true } ] }
```

| 结果 | 说明 |
|---|---|
| `success` / `fail` / `skipped` | 成功 / 失败 / 跳过（转换规则跳过）条数 |
| `results[].reason = "not_found"` | job=1 但简道云里查不到该主键 |
| `results[].reason = "transform_skip"` | 被转换规则跳过（飞霞"在线考试/其他市名"） |
| `results[].reason = "missing_pk"` | 该行缺 `pk` |
| `results[].reason = "no_fields"` | job=1 但除了 `pk` 没传任何业务字段 |

### B. 旧接口：`POST /api/sync/notify`（回查版，保留兼容）

旧接口仍可用：只传 `{table, pk, database?}`，本工具**回查源数据库**拿该行最新值，再判断增改。行为同最早版本，见历史文档。

> 新旧接口**并存**；新业务请优先用 `notify-batch`（对方直接带数据，省一次回查）。

## 四、后端实现逻辑

### 1. 处理流程（`POST /api/sync/notify-batch`）

```
1. 校验 table / rows / job(1或2)
2. 按 table（+ database）找到映射（mappings.json）
3. 逐行：
   a. 取 pk
   b. job=2：按映射组装全量记录（id=pk、数据类型、平台、全部业务字段）
      job=1：只组装对方传过来的字段（部分更新，不含 id/数据类型/平台）
   c. job=2 → batch_create（批量）
      job=1 → jdy_find_by_id(pk, 数据类型) 拿 data_id → 单条 update（只更新传入字段）
4. 汇总 success / fail / skipped + 每行结果
```

### 2. 新旧接口对比

| 项 | `notify-batch`（新） | `notify`（旧） |
|---|---|---|
| 对方传什么 | 表名 + job + 行数据（字段值） | 表名 + pk |
| 字段值来源 | 对方直接给 | 本工具回查源库 |
| 增改判断 | 对方用 job 指定 | 本工具查简道云判断 |
| 是否回查源库 | 否 | 是 |

## 五、简道云字段与映射设计

### 1. 简道云表单字段（实测）

| 字段 label | widget key | 用途 |
|---|---|---|
| id | `_widget_1789030761638` | 存源表主键（**匹配键之一**） |
| 数据类型 | `_widget_1789030761637` | 每张表写固定值（**匹配键之一**，全局唯一） |
| 平台 | `_widget_1788918827859` | 每张表写固定值 |
| 项目编号 | `_widget_1788918827860` | 业务字段（源字段映射） |
| 项目名称 | `_widget_1788918827861` | 业务字段（源字段映射） |
| 平台数据创建时间 | `_widget_1788918827862` | 业务字段（源字段映射） |

### 2. 「平台 / 数据类型」固定值（前端自动填充，见实现记录）

| 平台 | 数据类型（全局唯一） |
|---|---|
| 大平台后台系统 | 大平台班级（dpt_product） |
| 大平台后台系统 | 大平台期次（dpt_e-commerce） |
| 教务系统 | 教务北京（schema=BFEC） |
| 教务系统 | 教务上海（schema=SHFEC） |
| 教务系统 | 教务广州（schema=GZFEC） |
| 飞霞系统 | 飞霞（表=db_plan_positon） |

### 3. `mappings.json`（映射关系，前端「保存映射」写入）

每套映射字段：`id / source / database / table / source_fields / target_fields / transforms / platform_value / data_type_value / enabled`。

飞霞的映射带转换规则（示例）：

```json
{
  "id": "user-src-xxx-db_plan_positon",
  "source": "user-src-xxx",
  "database": "mexam3",
  "table": "db_plan_positon",
  "platform_value": "飞霞系统",
  "data_type_value": "飞霞db_plan_positon @mexam3---飞霞",
  "source_fields": ["ExamPlanName", "ExamAreaName", "ExamDate"],
  "target_fields": ["_widget_1788918827860", "_widget_1788918827861", "_widget_1788918827862"],
  "transforms": ["batch_number", "city_name", ""],
  "enabled": true
}
```

- `source_fields` / `target_fields`：源字段 → 简道云字段 key 一一对应；
- `transforms`：与 `source_fields` 等长，`batch_number`=提取批次号、`city_name`=市名+考场、空=无转换；`city_name` 遇"在线考试"/"其他"市名返回 None → 该行跳过；
- `platform_value` / `data_type_value`：写入简道云的固定值，`data_type_value` 参与匹配，**必须每张表唯一且非空**。

### 4. 写入简道云时每条记录固定带的字段

| 简道云字段 | 取值来源 |
|---|---|
| id（`JDY_ID_KEY`） | 行数据里的 `pk` |
| 数据类型（`JDY_TYPE_KEY`） | 映射的 `data_type_value` |
| 平台（`JDY_PLATFORM_KEY`） | 映射的 `platform_value` |
| 业务字段（source→target） | 行数据里的源字段值（套转换规则） |

## 六、三平台接入前提

1. **数据源改名**（用前端「数据源管理」）：`大平台后台系统`、`教务系统`、`飞霞系统`；
2. **每张表保存映射**（用前端「保存映射」按钮，id 自动生成）；
3. **Oracle 关掉合并模式**，每次只选单个 schema（BFEC/SHFEC/GZFEC）。

## 八、风险点

1. **回调漏掉**：无轮询兜底，若对方重试仍失败，该条数据会漏同步。建议二期补一个「补传」手段。
2. **组合键唯一性**：匹配依赖「主键 + 数据类型」组合唯一。主键每张表内唯一（已满足）；数据类型每张表唯一且非空（当前 6 个值已保证唯一）。
3. **job=1 依赖简道云 lookup**：修改仍需 `jdy_find_by_id` 查一次简道云拿 data_id，依赖 filter 语法（需联调验证；若不生效，回退为拉取字段 + 客户端比对）。
4. **单条 update 限流**：简道云 `update` 20 次/秒，瞬时大量修改会排队，回调场景变化量小、可接受。
5. **删除不同步**：简道云删除接口未授权，源表删除无法同步。

## 九、术语速查

| 术语 | 含义 |
|---|---|
| 回调 | 对方写库后主动调本工具接口 |
| job | 对方指定的操作类型：1=修改、2=增加 |
| data_id | 简道云每条数据的内部唯一编号 |
| 匹配键 | 用于定位简道云数据的唯一组合（本方案用「源表主键 + 数据类型」） |
| 转换规则 | 源字段值在写入前的加工（批次号提取、市名+考场） |
