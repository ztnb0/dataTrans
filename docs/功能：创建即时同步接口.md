# 功能：创建即时同步接口

> 分支：`feature/表单数据的即时同步功能`
> 本文档描述「即时同步接口」功能：对方业务系统在写库后主动回调本工具接口，本工具回查数据库后把变化写入简道云。
> 与本文档相关的历史讨论见 `docs/sync-feature-plan.md`（含五之补充、五.一 的 CDC 突破方案）。

---

## 一、背景与目标

### 背景

此前在 `sync-feature-plan.md` 中规划过三种实现"数据变化即时同步"的技术路线，经与老师沟通，逐条收敛如下：

| 路线 | 结论 |
|---|---|
| 轮询（定时查库） | 实时性差、有数据库压力，且无回调的情况下才需要 |
| CDC（binlog / DTS / canal） | 太麻烦：需要权限、组件、Kafka 等，被否决 |
| **回调（对方改库后调接口）** | **最终选定**：最简单、最贴合业务 |

### 目标

对方业务系统在数据库上做**新增（INSERT）**或**修改（UPDATE）**并提交后，主动调用本工具的接口，本工具回查数据库最新值，把对应变化同步到简道云对应的表单字段。

---

## 二、方案概述

```
对方业务系统 INSERT/UPDATE 成功、commit 之后
  → 调本工具接口 POST /api/sync/notify（只传：哪张表 + 哪个主键）
  → 本工具回查数据库，拿到这一行最新值
  → 按简道云「id + 数据类型」组合键定位（有则 update / 无则 batch_create）
```

核心设计原则：

1. **对方传得越少越好**：对方只传「表名 + 主键」，字段值由本工具回查数据库为准，避免对方拼字段出错、也保证永远与库一致。
2. **用「源表主键 id + 数据类型」组合键精确定位**：简道云表单新增了「id」字段存源表主键，与「数据类型」字段组合作为唯一匹配键（两张表各自 id 都从 1 开始、会跨表重叠，单用 id 会撞车，必须加数据类型区分）。
3. **无鉴权**：公司内网自用、接口不对外，不做 token 鉴权，任何人可调。

---

## 三、接口契约

### 1. 地址

| 项 | 值 |
|---|---|
| 方法 / 路径 | `POST /api/sync/notify` |
| 协议 | HTTP，内网直连，**无鉴权** |

### 2. 请求体

```json
{
  "table": "coaching_class",
  "pk": "123"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `table` | string | 源表名（如 `coaching_class`、`groupbatch`） |
| `pk` | string | 该行主键值（统一按字符串传） |

### 3. 响应

| 场景 | 状态码 | 响应体 |
|---|---|---|
| 成功 | 200 | `{"ok": true, "action": "create" | "update"}` |
| 表未配置映射 | 400 | `{"detail": "..."}` |
| 参数缺失 | 400 | `{"detail": "..."}` |
| 处理异常 | 500 | `{"detail": "..."}` |

### 4. 对方要做的事

在对方写库的代码里，insert/update 提交成功后加一行**异步**调用（不阻塞主业务，失败重试 2~3 次）：

```python
# 伪代码示意（对方语言自定）
def save_record(...):
    db.insert_or_update(...)   # 原有逻辑
    db.commit()
    # 新增：异步通知本工具，失败重试
    requests.post('http://<内网IP>:8088/api/sync/notify',
                  json={'table': 'coaching_class', 'pk': 123},
                  timeout=5)
```

## 四、后端实现逻辑

### 1. 处理流程（`POST /api/sync/notify`）

```
1. 校验 table / pk 参数
2. 按 table 找到对应映射（mappings.json）
3. 回查数据库该行（自动 get_primary_key 取主键）
4. 按「id + 数据类型」查：jdy_find_by_id(pk, 数据类型)
   ├─ 查到 data_id → 单条 update（更新 id/数据类型/平台 + 业务字段）
   └─ 查不到       → batch_create（写入 id/数据类型/平台 + 业务字段）
5. 返回 {ok: true, action: "create" | "update"}
```

### 2. 新增 vs 修改的判断

| 简道云「id == pk 且 数据类型 == data_type_value」 | 动作 |
|---|---|
| 查不到 | `batch_create` 新增 |
| 查到 data_id | 单条 `update` |

> 简道云表单从空开始，之后每次写入都会带上源表 id 和数据类型，所以"是否有这条"用「id + 数据类型」组合判断即可，无需本地状态文件。

### 3. 需要新增/复用的代码（相对现有 `app.py`）

| 模块 | 说明 | 现状 |
|---|---|---|
| `POST /api/sync/notify` | 回查 + 按 id+数据类型 定位 + 新增/修改 | ❌ 新增 |
| `jdy_find_by_id` | 按「id + 数据类型」查 data_id | ❌ 新增 |
| 单条 `update` 函数 | 复用 `normalize_value` + 简道云地址/token | ❌ 新增 |
| `batch_create` | 已有 | ✅ 复用 |
| `get_conn` / 查询逻辑 | 回查该行 | ✅ 复用 |

## 五、简道云字段与映射设计

### 1. 简道云表单字段（实测）

| 字段 label | widget key | 用途 |
|---|---|---|
| id | `_widget_1789030761638` | 存源表主键 id（**匹配键之一**） |
| 数据类型 | `_widget_1789030761637` | 每张表写固定值（**匹配键之一**，如"班级"/"期次"） |
| 平台 | `_widget_1788918827859` | 每张表写固定值 |
| 项目编号 | `_widget_1788918827860` | 业务字段（源字段映射） |
| 项目名称 | `_widget_1788918827861` | 业务字段（源字段映射） |
| 平台数据创建时间 | `_widget_1788918827862` | 业务字段（源字段映射） |

### 2. `mappings.json`（映射关系，界面/配置维护）

```json
[
  {
    "id": "coaching-class",
    "source": "dpt-aliyun",
    "database": "dptep",
    "table": "coaching_class",
    "platform_value": "教务系统",
    "data_type_value": "班级",
    "source_fields": ["class_number", "class_name", "class_ctime"],
    "target_fields": ["_widget_1788918827860", "_widget_1788918827861", "_widget_1788918827862"],
    "enabled": true
  },
  {
    "id": "groupbatch",
    "source": "dpt-aliyun",
    "database": "dptep",
    "table": "groupbatch",
    "platform_value": "教务系统",
    "data_type_value": "期次",
    "source_fields": ["classnumber", "batchName", "createDate"],
    "target_fields": ["_widget_1788918827860", "_widget_1788918827861", "_widget_1788918827862"],
    "enabled": true
  }
]
```

- `id_field_key`（简道云「id」字段）写死为常量 `JDY_ID_KEY`，不在映射里重复配；
- 数据类型、平台为**固定值**，分别存 `data_type_value` / `platform_value`；其中 `data_type_value` 参与匹配，**必须每张表唯一且非空**；
- `source_fields` / `target_fields` 为业务字段一一对应；
- 主键由 `get_primary_key` 自动获取（coaching_class / groupbatch 均为 `id`）。

### 3. 写入简道云时每条记录固定带的字段

| 简道云字段 | 取值来源 |
|---|---|
| id（`JDY_ID_KEY`） | 源表主键值 |
| 数据类型（`JDY_TYPE_KEY`） | 映射的 `data_type_value` |
| 平台（`JDY_PLATFORM_KEY`） | 映射的 `platform_value` |
| 业务字段（source→target） | 源表对应字段值 |

## 八、风险点

1. **回调漏掉**：无轮询兜底，若对方重试仍失败，该条数据会漏同步。建议二期补一个「补传」手段。
2. **组合键唯一性**：匹配依赖「id + 数据类型」组合唯一。id 每张表内唯一（主键，已满足）；数据类型每张表唯一且非空（当前 班级 / 期次 满足）。若以后多张表共用同一数据类型值，会再次撞车，需换方案（id 加表名前缀）。
3. **简道云 list 的 filter 语法**：`jdy_find_by_id` 依赖简道云按字段精确过滤（两个条件），需联调验证；若 filter 不生效，需回退为"拉取 id/数据类型字段 + 客户端比对"。
4. **单条 update 限流**：简道云 `update` 20 次/秒，瞬时大量修改会排队，回调场景变化量小、可接受。
5. **删除不同步**：简道云删除接口未授权，源表删除无法同步。

## 九、术语速查

| 术语 | 含义 |
|---|---|
| 回调 | 对方写库后主动调本工具接口 |
| 回查 | 本工具收到通知后重新查数据库拿最新值 |
| data_id | 简道云每条数据的内部唯一编号 |
| 匹配键 | 用于定位简道云数据的唯一组合（本方案用「源表主键 id + 数据类型」） |
