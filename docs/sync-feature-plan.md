# 表单信息即时同步功能 — 任务文档

> 分支：`feature/表单数据的即时同步功能`
> 本文档记录本分支要做的功能、背景、方案、约束与待办，便于日后查阅和理解。

---

## 一、背景与目标

### 现状问题
目前工具已完成「手动传输」：用户在前端选数据源 → 选表 → 勾字段 → 配映射 → 预览确认 → 全量写入简道云。

存在两个缺陷：
1. **映射关系是临时的**：每次刷新页面都要重新配置，没有持久化。
2. **只支持全量重传**：每次传输都把源表所有数据重新 `batch_create` 一遍，没有"增量"概念，无法感知"新增/修改"。

### 目标
把「数据源 ↔ 简道云」的字段映射关系**固定保存**下来，后台**自动轮询**检测源数据变化，把**新增**和**修改**的数据**增量同步**到简道云对应表单。

---

## 二、核心概念（大白话解释）

### 1. 映射持久化
把用户配好的「字段对应关系」保存到本地 JSON 文件，重启后自动加载，不用每次重新配置。

### 2. 对账（首次建立对应关系）
简道云里已有数据，但没记录「源表主键 ↔ 简道云 data_id」的对应关系。

- 简道云每条数据有个内部编号 `data_id`，只有写入那一刻才会返回给我们。
- 之前手动同步的数据没保存这个对应关系，导致将来"更新"时不知道改简道云里哪一条。

**对账**：第一次跑同步时，用「项目编号」这个唯一标识，把数据库每一行和简道云已有数据一一对应，补记下 `data_id`。**只在第一次做一次**，做完存入 `sync_state.json`。

### 3. 增量同步
只同步"变化的"数据，而不是每次全量重传：
- **新增**：源表新插入的行 → 写入简道云
- **修改**：源表已有行字段值变了 → 更新简道云对应数据

### 4. 轮询
后台定时任务每隔一段时间（本方案 5 分钟）自动检查一次源数据变化并同步。不需要每次手动操作。

---

## 三、已确认的需求决策

| 项 | 决策 |
|---|---|
| 同步触发方式 | 后台轮询，每 **5 分钟** 自动一次 |
| 新增检测 | 主键递增（`id > 上次最大id`） |
| 修改检测 | 混合策略（见下） |
| 存储方式 | JSON 文件 |
| 对账唯一键 | 项目编号 |
| 更新方式 | 单条 `update` 接口 |
| 同步范围 | 所有已建立映射的数据源（含以后新增的数据源） |
| 同步任务面板 | 暂不做，先用日志文件查看同步结果 |

## 四、关键约束（已实测确认）

### 1. 简道云 API 限制
| 接口 | 情况 |
|---|---|
| `batch_create` 批量新增 | ✅ 可用，返回 `success_ids`（按顺序对应） |
| `update` 单条更新 | ✅ 可用，需要 `data_id` |
| `batch_update` 批量更新 | ⚠️ 只能把多条数据**改成同一个固定值**，无法逐条设不同值 |
| `delete` / `batch_delete` | ❌ 未授权 |

**影响**：修改同步只能用**单条 `update` 逐条更新**（频率 20 次/秒）。增量场景每次变化量小，可接受。

### 2. 源表"修改时间戳"字段情况
| 表 | 主键 | 修改时间戳 | 能否加字段 |
|---|---|---|---|
| `groupbatch`（MySQL 期次） | `id` | ✅ 有 `mtime` | — |
| `coaching_class`（MySQL 班级） | `id` | ❌ 无 | ❌ 无权限 |
| Oracle `CLAZZ`（班级） | `CLASS_ID` | ❌ 无 | ❌ 只有 CREATE SESSION |

**影响**：修改检测无法统一用时间戳，需混合策略（见下）。

### 3. Oracle 环境
- 版本 10g（10.2.0.5.0），需 Instant Client 21 + thick 模式（详见 `oracle-plan.md`）
- 表分布：`BFEC`/`SHFEC`/`GZFEC` 三个 schema 的 `CLAZZ`
- 字符集 `ZHS16GBK`

## 五、技术方案

### 1. 数据文件设计

**`mappings.json`**（映射关系，界面保存，可多套）
```json
[
  {
    "id": "oracle-clazz",
    "name": "Oracle班级同步",
    "source": "oracle-clazz",
    "schemas": ["BFEC", "SHFEC", "GZFEC"],
    "table": "CLAZZ",
    "platform_value": "教务系统",
    "source_fields": ["CLASS_CODE", "CLASS_NAME", "BEGIN_YEAR"],
    "target_fields": ["_widget_...860", "_widget_...861", "_widget_...862"],
    "time_field": "BEGIN_YEAR",
    "enabled": true
  }
]
```

**`sync_state.json`**（同步状态，后台自动维护）
- 每套映射记录：
  - `max_id`：上次同步到的最大主键
  - `rows`：`主键 → { data_id, hash }` 的对应关系
  - `last_sync_time`：上次同步时间

### 2. 同步流程（每次轮询，对每套映射）

1. **对账（首次，`max_id` 为空时）**
   - 拉取简道云已有数据的 `项目编号 ↔ data_id`
   - 源表全量读入，按项目编号匹配：
     - 已在简道云的 → 记 `data_id` + 值 hash（接管）
     - 不在的 → 标记为待新增
   - 写入 `sync_state.json`

2. **增量检测**
   - 新增：`id > max_id` 的行 → `batch_create`，记录返回 `data_id`
   - 修改（有 `mtime` 的表）：`mtime > 上次时间` → 单条 `update`
   - 修改（无时间戳的表）：全量拉主键+映射字段算 hash，与快照对比 → 单条 `update`

3. **更新同步状态**：刷新 `max_id`、`data_id` 映射、hash 快照、同步时间

### 3. 混合修改检测策略

| 表 | 新增检测 | 修改检测 |
|---|---|---|
| `groupbatch` | 主键递增 | `mtime` 时间戳 |
| `coaching_class` | 主键递增 | 轻量全量 hash 对比 |
| Oracle `CLAZZ` | 主键递增 | 轻量全量 hash 对比 |

> 轻量全量对比只查「主键 + 映射的 3~4 个字段」（非 `SELECT *`），9481 行约 1MB、<1 秒，5 分钟一次无压力。

### 4. 界面与后端改动

- 前端：映射面板加「保存映射」按钮 → 写 `mappings.json`
- 后端新增接口：
  - `GET/POST /api/mappings`：读写映射
  - `GET /api/sync/status`：各映射同步状态
  - `POST /api/sync/run`：手动触发某套映射同步
- 后台定时任务：每 5 分钟跑 `run_all_sync()`，结果写日志文件

## 六、风险点

1. **对账只做一次**：首次对账建立映射后持久化，之后不再对账。若期间有人手动改了简道云数据，会导致映射失真。
2. **项目编号唯一性**：现有数据无空无重复，但若源表新数据出现重复项目编号，会导致匹配歧义 → 需告警并跳过。
3. **单条 update 性能**：大量行同时修改时逐条 update 会慢，但增量场景变化量小，可接受。
4. **删除未同步**：源表删除行，简道云不会同步删除（删除接口未授权）。本方案不含删除同步。

## 八、术语速查

| 术语 | 含义 |
|---|---|
| 对账 | 首次运行，把简道云已有数据与源表按唯一键对应，补记 data_id |
| 增量同步 | 只同步新增/修改，不全量重传 |
| data_id | 简道云每条数据的内部唯一编号 |
| 主键递增 | 用 `id > 上次最大值` 判断新增 |
| hash 对比 | 对字段值算哈希，与上次快照比对判断是否修改 |
| 轮询 | 后台定时自动检查并同步 |
